# /pr-check reference: steps 4.8 / 4.9: unresolved threads, round-4 cap

4.8. **Unresolved-thread gate (HIMMEL-949) — blocking, skipped only when no PR exists yet.** All PR review comments must be resolved before the gate clears — an unresolved thread (e.g. a CodeRabbit App comment) is a merge blocker exactly like a Critical finding. It does NOT certify that the head was reviewed: the review-freshness leg (HIMMEL-1181) is retired by HIMMEL-3360, because CodeRabbit is best effort and an unreviewed head is not a gate outcome. This step delegates to `scripts/check-ci.sh --threads-only` (paginated reviewThreads query + review-body-findings query, fail-closed on query errors), the same gate `/check-ci` runs at merge time.
   ```bash
   threads_rc=2  # default: unknown = blocking; every path below overwrites it
   pr_rc=0
   # --head takes step 0's printed `branch=` LITERAL (HIMMEL-2226),
   # SINGLE-QUOTED: pasted bare, a branch name is shell-parsed.
   pr_lookup=$(gh pr list --state open --head '<branch>' --json number --jq '.[0].number' 2>&1) || pr_rc=$?
   if [ "$pr_rc" -ne 0 ]; then
       echo "4.8: gh pr list failed ($pr_lookup) — thread state UNKNOWN, treat as BLOCKING" >&2
   elif [ -z "$pr_lookup" ]; then
       echo "4.8: no PR yet — thread gate NOT RUN (it cannot be: there are no threads before a PR exists). This run says NOTHING about review threads. The CodeRabbit App reviews only AFTER gh pr create, so its findings appear after this gate has already cleared the marker — /check-ci is what enforces them, at merge time (HIMMEL-1125)."
       threads_rc=0
   else
       threads_rc=0
       threads_out=$(bash "<himmel_dir>/scripts/check-ci.sh" --threads-only 2>&1) || threads_rc=$?
       printf '%s\n' "$threads_out"
   fi
   echo "4.8: threads_rc=$threads_rc"
   ```
   `threads_rc` is the single status steps 5/6 consume — the no-PR skip sets it to 0 (pass) explicitly, so no path leaves it undefined:
   - `threads_rc = 0` → gate passed (zero unresolved threads, or no PR yet). Relay any `check-ci: … (CodeRabbit body: nitpick=… additional=…, non-blocking)` suffix and any `check-ci: NOTE — CodeRabbit …` line on the printed output into the `/pr-check` report VERBATIM — a non-zero body-finding count is surfaced, never silenced (HIMMEL-1147/1148 disposition contract: fix it, file a ticket, or a one-line "declined, reason" in the PR body).
   > **A clean `/pr-check` is NOT a clean thread state** (HIMMEL-1125) — different signals at different times. This gate runs at PRE-PUSH; the CodeRabbit App reviews only after `gh pr create`. On PR #1262 the panel returned 0/0/0, the marker cleared, the PR opened — and *then* `check-ci` returned `exit=3`: one unresolved App thread carrying a real finding. It recurred on PR #2209 (2026-09-06) with six unresolved threads sitting under a `pass` check-run — a green rollup is not a clean thread state either. Nothing in the pre-push flow can catch that. So after opening or refreshing a PR, **loop `scripts/check-ci.sh` until it exits 0** before any merge, handover, or "the PR is done" claim. Operator directive 2026-07-17: *"keep pulling until PRs are green and no unresolved comments from CodeRabbit."* Zero-token watcher: the `check-ci` skill.
   - **A PR that changes `.github/workflows/*.yml` dispatches each changed workflow BEFORE `READY`, not at the GO (HIMMEL-7104).** The chief's `ready-check.sh` check 10 needs a completed `workflow_dispatch` run at the PR head, so after the push run `gh workflow run <file>.yml --ref <branch>` once per changed workflow that is not on `WF_DISPATCH_EXEMPT` in `ready-check.sh`, wait for it with `gh run watch <id>`, and put every run id in your `READY` bullet as `dispatch: <file>.yml=<id>`. A failed run is yours to read: `ready-check.sh` passes it as a `PRE-EXISTING` line only when every failed job of it also failed in main's latest scheduled/push run of that workflow; a job red only on the PR is a new failure, fix it. Re-dispatch after every push, since a run at an older head proves nothing.
   - ANY other `threads_rc` → BLOCKING in step 6 — 3 = unresolved threads, changes requested, or an outside-diff-range body finding; 4 = retired (HIMMEL-3360: the review-freshness leg no longer exists, so this code is never emitted — a script that still expects it is stale); 2 = the thread or body-findings lookup failed (fail-closed; CodeRabbit's own status never produces this code); 64 = usage error, NO gate ran (HIMMEL-3317 — fix the command line; step 4.8 passes only `--threads-only`); and any unexpected code is treated the same: address each comment, resolve its thread (always resolve the thread when fixing a CR finding), then re-run.

4.9. **Round-4 cap disposition (HIMMEL-2780; only when step 3.0 printed round 4 or later, or round 2 or later on a Suggestions-only round of a PR that touches no CI trust path (step 6)).** The current head's round-4+ panel has already executed and produced its rows; the cap removes the **next correction review**, not this review or any future fresh head's required review. Run this only after every producer has written its rows and steps 3.2–4.8 have finished, and only when step 3.6 reported `impacted_rc = 0` — the script clears the marker itself and does not read `impacted_rc`, so with a non-zero one skip it and follow step 6 (HIMMEL-2821); `panel-first-pass.sh` deliberately does not clear early. Critical or Important findings block at every full round. **In the delta round (HIMMEL-4600) only Critical or escape-class (`fu_class=escape`) findings block;** every open Important must first be classified by you with an explicit amend, `ledger-append.sh amend --branch '<branch>' --head <head> --id '<id>' --set fu_class=escape|hardening --reason '<why>'` — escape-class is fixed in this PR, never deferred, and `defer` refuses (exit 4, naming each id) while any Important lacks the amend; a classified-hardening Important is then deferred to the same ticket as `fu_class=hardening`, a suggestion/nit as `fu_class=polish`, each with the reason `Finding deferred in the one delta round after the three-round /pr-check cap.` — so `clear-cr-marker.sh` accepts the delta round's rows at the new head. For round 4+, leave suggestion/nit producer rows unamended in step 4.5 and pass the PR's **one** tracking ticket here; the script reads those existing rows (it never reruns or retypes a reviewer), appends `deferred` amendments with the ticket and reason through `ledger-append.sh` while preserving each row's artifact/perspective identity, preserves existing valid verdict scratch lines while writing the cap dispositions through `write-verdicts.sh`, then invokes `clear-cr-marker.sh` itself:
   ```bash
   bash "<himmel_dir>/scripts/cr/review-round.sh" defer \
       --head <head> --branch '<branch>' --defer-to HIMMEL-<n>
   ```
   `CR_DEFER_TO=HIMMEL-<n>` is the process-environment alternative; `--defer-to` wins when both are present. Exit 4 means an unresolved Critical/Important finding remains (Critical/escape-class in the delta round): leave the marker and follow step 6. If deferrable rows exist but no valid ticket was supplied, the script files each through the primary checkout's `jira create --residual-of` verb. The parent is the first ticket key in the one open PR's title; Suggestions/nits use `--fu-class polish`, deferred Important findings use `--fu-class hardening`, and a finding's class id is forwarded when present. A classless finding carries `class: unclassified` in its residual body, with no invented class label. The Jira verb alone decides depth and version routing. Exit 6 means the parent could not be resolved or creation failed: keep the marker and recover with `review-round.sh defer --head <head> --branch '<branch>' --defer-to HIMMEL-<n>` against the same captured head, without another paid panel run. A retry after amendments persisted but verdict-scratch writing or marker clearance failed recognizes those cap-deferred rows, repairs both scratch files without discarding prior valid verdicts, and re-attempts the sanctioned clear. When the script prints `CR clean — marker cleared`, step 5 is already complete; do not invoke the clearance script a second time. Only when neither unadjudicated suggestion/nit rows nor a recoverable cap disposition exists does it exit 0 without clearing and leave the normal step-5 decision to apply.
