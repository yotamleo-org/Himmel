`2621-2623`: **🩺 Stability & Availability** | **🔵 Trivial**

**The reap deletes the lock by pathname after the CAS check.**

The check at Line 2613 compares `owner.json` content. The `rm -rf "$lockdir"` at Line 2622 then deletes by path. Suppose the dead holder's lock is released and a new session acquires it between the check and the `rm`. The reap then deletes the new holder's live lock. The takeover claim does not stop this, because a plain `acquire` takes the `mkdir` fast path when the lock dir is missing and does not check the claim. The in-code comment accepts this window. The window is narrow, and the holder is already proven dead, so a concurrent release by that holder is unlikely. The fix would rename the lock dir to a reap-private path, re-verify `owner.json` there, and then delete it. This item is noted only. A fix is not required before merge.
