# luna-ingest — Phase 3.7 — Advisory skill scan (`--skill-scan` only)

Skip this entire phase unless `--skill-scan` was passed. Runs after Phase 3.6 and before Phase 4. It runs SkillSpector over each skill directory in the source repo and stores the JSON reports with the note. It never changes `trust_tier`, `safety_flag`, `repo_scan` or the Phase 1.5 outcome, and never changes the ingest rc. The pilot found Stage 1 flags real patterns but also false positives on clean skills, and it never returns SAFE alone; do not read a clean report as a pass.

**Two modes, by provider.** A plain read-through of a repo is advisory: `SKILLSPECTOR_PROVIDER=ollama` runs Stage 1 only (static, `--no-llm`), so no skill text goes to an LLM (the OSV lookup below still runs unless `SKILLSPECTOR_OFFLINE=1`), and a finding means "read the flagged line before adopting or using the skill". **A skill is a vendor candidate only when the ingest request says it is to be vendored; every other `--skill-scan` use, a `/harvest-clips` clip included, is a read-through and takes `ollama`. A vendor candidate takes the full scan, and it is a required step of vendoring; with no key it is `not scanned (rc 2)`, never an `ollama` substitute**: `SKILLSPECTOR_PROVIDER=nv_build` with `NVIDIA_INFERENCE_KEY` in the environment, or `SKILLSPECTOR_PROVIDER=anthropic` with `ANTHROPIC_API_KEY`. That runs Stage 1 with the live OSV lookup plus Stage 2, the AI review, and it sends the skill text to the provider. A HIGH or CRITICAL finding that survives Stage 2 stops the vendoring (wrapper rc 4) until a person has read the flagged line and recorded its fingerprint in `<report>.ack`. Never read a key out of `.env`; the operator exports it in the launching shell.

1. **Dry-run and existing-note short-circuit.** With `--dry-run`, print `DRY luna-ingest: would run skill scan for <owner_repo>` to stderr, set `skill_scan: unavailable`, and continue to Phase 4. When the Phase 4 target note already exists (Phase 4 will refuse with rc=3), skip the scan the same way, so no report is written or overwritten beside a note that is not rewritten.
2. **Find the skills.** A skill is a directory holding a `SKILL.md`. List them from the repo tree through `gh api` (`git/trees/<ref>?recursive=1`, entries ending `/SKILL.md` or a root `SKILL.md`). `<ref>` is the default branch, or the `<branch>` of a `/tree/<branch>/<path>` input URL. Resolve it to a commit sha once (`gh api repos/<owner_repo>/commits/<ref> --jq .sha`) and use that sha for the tree listing and for every contents fetch in step 3, so the scanned text is one revision of the clipped text. If the tree response has `truncated: true`, the listing is partial: record `skill_scan: unavailable` and continue to Phase 4, never `clean`. When the input URL named a `/tree/<branch>/<path>` directory, scan only the skill directories under that path. Scan at most 5 skills; list the rest in the section as `not scanned (cap)`.
3. **Fetch text only.** For each skill, make a throwaway directory and write that skill's files (every file under the skill directory in the recursive tree listing, subdirectories included) into it through `gh api` contents at `?ref=<sha>`, the pinned commit sha from step 2 (files up to 200 KB, no clone, nothing executed). A file over 200 KB, or one that fails to fetch, is omitted from the directory and the skill is marked `incomplete`; an `incomplete` skill is never counted `clean` and the section lists it as `not fully scanned (<file>)`:

   ```bash
   skill_tmp="$(mktemp -d "${TMPDIR:-/tmp}/luna-ingest-skill.XXXXXX")" || skill_tmp=""
   ```

   If `skill_tmp` is empty (the directory could not be created), record `skill_scan: unavailable` and continue to Phase 4; this phase never changes the ingest rc.

   Write the skill's files directly into `$skill_tmp` (one throwaway directory per skill, removed after its scan). `<skill-slug>` names only the report: the slugified repository-relative skill path (`[a-z0-9-]`, `/` becomes `-`) followed by `-` and the first 8 hex characters of the sha256 of the unslugified path, so `skills/a-b` and `skills/a/b` never share a report; a root skill uses `root`.
4. **Scan through the one wrapper.** Set the provider on purpose: upstream defaults an unset provider to `nv_build`, which sends the skill text to build.nvidia.com, so the wrapper refuses an unset provider. `ollama` is Stage 1 only; `nv_build` and `anthropic` are the full scan for a vendor candidate and refuse (rc 2) with a named reason when `NVIDIA_INFERENCE_KEY` / `ANTHROPIC_API_KEY` is missing, and with `SKILLSPECTOR_OFFLINE=1` (Stage 2 needs the network). Stage 1 posts the skill's lockfile package names and versions to api.osv.dev to check them for known CVEs; that lookup stays on. Only for a private skill whose dependency list must not leave the machine, also set `SKILLSPECTOR_OFFLINE=1`: the wrapper then runs the scanner with the network denied (`unshare --user --net`), skips the live CVE lookup, and refuses (rc 2) on a host where it cannot deny the network.

   ```bash
   export SKILLSPECTOR_PROVIDER=ollama     # read-through: every use not named for vendoring, clips included
   export SKILLSPECTOR_PROVIDER=nv_build   # vendor candidate only (or anthropic): the ingest request says the skill is to be vendored
   bash "<plugin>/tools/skillspector-scan.sh" "$skill_tmp" "<vault>/<dest>/<repo-slug>.skillspector/<skill-slug>.json"
   ```

   Create `<repo-slug>.skillspector/` next to the note first and apply the Phase 4 path-safety check to it. The wrapper prints `skillspector-scan: score=<n> issues=<k> high=<h>`, followed by `deps=offline-fallback` when `SKILLSPECTOR_OFFLINE=1` was set and the skill has a lockfile: its dependencies were checked against SkillSpector's small built-in list, not OSV. Copy that word onto the skill's section line. Remove `$skill_tmp` afterwards. In the full scan the report also carries the scanner's stderr under `wrapper_stderr` (keys redacted). SkillSpector is never installed here: any non-zero wrapper rc (1 not a directory, 2 refused provider, missing provider key, or `SKILLSPECTOR_OFFLINE=1` with no network denial on this host or with Stage 2, 3 missing binary, bad report, symlinked report path, or a Stage 2 that did not run, 4 blocked) means that skill was not cleared: list it as `not scanned (rc <n>)`, never `clean`. rc 4 is different from the rest: the report **is** stored, so list it as `blocked (rc 4)` with the report link and the unacknowledged `<file>:<line> <pattern> fingerprint=<fp>` lines the wrapper printed, and the vendoring does not proceed until a person has read each line and written its fingerprint into `<report>.ack`, then the wrapper run again returns rc 0. Install SkillSpector only in a throwaway sandbox or the test VM.
5. **Record in the synthesis:**
   - Frontmatter `skill_scan: clean | flagged | unavailable`: `flagged` when any scanned skill has `issues` above 0, `unavailable` on any non-zero wrapper rc for any skill or no skill found (rc 4 counts as `flagged`: the report exists and holds a HIGH), else `clean`. A partial run is never `clean`: when the cap left skills unscanned or any skill is `incomplete`, the result is `flagged` if any scanned skill has `issues` above 0, else `unavailable`.
   - A `## Skill scan (advisory)` section: one line per skill as `` `<skill>`: score=<n> issues=<k> high=<h>, report [[<repo-slug>.skillspector/<skill-slug>.json]] ``. When `high` is above 0 add `read the flagged line before adopting`. Quote nothing from the skill text; the report holds the detail.
