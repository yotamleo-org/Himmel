Plan & hand outfrom your himmel clone

The chief, a long-running session you talk to, turns tickets into work. Tickets that touch different files start together as a parallel wave; a ticket that needs another one merged first waits in a dependency chain. Which release a ticket belongs to is the release manager's ruling, not the chief's.

2 The loop inside this step

  1. Pick the next ticket
  2. Check it collides with no running worker
  3. Write the brief and the worktree
  4. Start the worker

3 What decides each move

Starting a worker

  1. A top-tier worker (opus, fable) without a stated reason?the worker startRefuseBack to the brief, which must say why.
  2. Is the fleet at its size cap?the usage check in your projectWaitThe chief waits until a worker finishes.
  3. Is this lane's usage bank used up? (the usage check says the budget is spent)the worker startRefuseThe launch is refused: park the ticket and retry later. A stale or unknown bank reading does not stop the launch.
  4. OtherwiseAllowThe worker starts in its own window, with a one-time token for later changes of plan.

Build in a worktreein your project

Each change is built in its own worktree, a second folder on its own branch, so main stays untouched. One worker, one ticket, one pull request.

2 The loop inside this step

  1. Write a failing test
  2. Change the code
  3. Run the tests
  4. Fix until green
  5. Commit

3 What decides each move

Starting the worktree

  1. Is the branch name a type/slug (feat, fix, chore, docs, refactor, test)?the worktree checkRefuse if notPick a name such as feat/login.
  2. Are too many worktrees open already?the worktree checkRefuseReclaim merged ones, or raise the worktree limit with its environment switch; Settings has no control for it yet.
  3. Does that branch name belong to a pull request that already merged?the worktree checkRefusePick a fresh name. Skipped with a warning when the forge cannot be reached.
  4. Otherwisefrom origin/<default branch>, or your local default branch when there is no remoteAllowThe worktree check names the folder to start Claude in.

What if

Committing

  1. Committing on main?the worktree isolation checkRefuseERROR: Committing directly on 'main' is not allowed. Commit in your worktree.
  2. Does the message start with a type: feat:, fix:, chore: …?the commit message checkRefuse if notCOMMIT REJECTED: message does not match conventional commit format.
  3. Does it name a ticket in your tracker's form: #1 by default, or your Jira key such as ABC-123?the commit message checkRefuse if notNo tracker? Turn the ticket-ID rule off in Settings.
  4. OtherwiseAllowThe commit is made.

What if

Guardrailsin your project

Before Claude Code runs any tool, himmel's hooks check it. Each hook that matches the tool sees the call; any one that says no stops it before anything happens. Git gates do the same for commits and pushes.

2 The loop inside this step

  1. Claude asks to run a tool
  2. The hooks for that tool check the call
  3. Refused: Claude reads why and changes course
  4. Allowed or asked: the call runs

3 What decides each move

Every tool call

  1. An edit in a repo that is on main?the edit-on-main guardRefuseMake a worktree first. Once, on purpose: start Claude with the edit-on-main off switch.
  2. Reading .env, a key file or another secret?the secrets guardRefuseKeys stay out of Claude's context. Once: start Claude with the secrets off switch.
  3. A destructive command: rm -rf, git reset --hard, git clean -f, a force push?the destructive-command guard on by defaultRefuseOnce: start Claude with the destructive-command off switch.
  4. A read-only look: ls, git log, grep and the like?the safe-read approverAllowRuns without a prompt, even inside a pipe.
  5. Anything elseClaude Code's own permission settingsAskThe same prompt you get without himmel.

What if

Every push

  1. Pushing to main?the push-target checkRefuseERROR: Direct push to 'main' is not allowed. There is no bypass: changes reach main through a pull request.
  2. A force push to main?the force-push checkRefuseERROR: Force-push to 'main' is not allowed. To another branch it goes through with a warning.
  3. Code changed since the last clean review?the review-before-push check from your himmel cloneAllow, review owedThe push goes through and leaves a review-owed marker, which the pull-request check reads.
  4. Script changes with no Platforms tested: line in a commit or the PR body?the platforms-tested check from your himmel cloneRefuseName the systems you tested on, such as Platforms tested: linux, in the branch's first commit.
  5. Code changes with no Security reviewed: line in a commit or the PR body?the security-reviewed check from your himmel cloneRefuseSay how you checked it, such as Security reviewed: manual — <what you did>, in the branch's first commit.
  6. OtherwiseAllowThe branch is on the remote.

What if

Tests & CIin your project

Your own CI runs on every push. The CI reader waits once in the foreground and its exit code is the answer, so nobody guesses whether a run is green.

2 The loop inside this step

  1. Push
  2. CI runs
  3. Red: back to the worktree
  4. Green and resolved: on to the gate

3 What decides each move

Reading the result

  1. A check failed? (exit 1)the CI readerBack to BuildA red job on your pull request is yours to fix.
  2. Green, but review threads are open? (exit 3)the CI readerBack to reviewAnswer and resolve the threads.
  3. GitHub will block the merge? (exit 5 or 6)the CI readerAskA branch rule or a conflict: your call.
  4. Cannot tell yet? (exit 2)the CI readerWaitRun the CI reader again, or repair the read.
  5. Green and resolved (exit 0)the CI readerAllowReady to merge.

What if

Second-model reviewfrom your himmel clone

The automated review has a second model family review the diff: OpenAI GPT through the Codex CLI, with Claude over the API when that lane is on. A finding you agree with sends the change back to the worktree; a pull request cannot open until the review has run, except in a starter install, which does not add that check.

2 The loop inside this step

  1. Review round
  2. Findings
  3. Agree: fix and push
  4. Next round, three at most
  5. Clean: the review is marked done

3 What decides each move

Each review round

  1. A blocking finding that you agree with?the automated reviewBack to BuildFix it, push again, and a new review round starts.
  2. Three full rounds used already?the review roundAskOne diff-only round may follow, and it blocks only on critical findings or ones that show a flow broken today. A judge NO-GO, every finding of that round fixed, or a red CI run buys one more bounded diff-only round. A fourth full round is refused.
  3. Cleanthe review-done markerAllowThe review-owed marker is cleared.

What if

Opening the pull request

  1. Is a review still owed for this branch?the review-before-PR checkRefuseOpening the pull request waits for a clean review.
  2. OtherwiseAllowThe pull request opens. In a starter install this check is not installed, so it always opens.

What if

Merge gatein your project

One gate sees everything the earlier steps produced: CI on this exact commit, the reviewers and CodeRabbit's review threads. Any merge Claude tries goes through it. It refuses on what it can read; a failed read lets the merge through with a warning, except in a clone armed with the CodeRabbit app, where an unreadable review ledger holds every required reviewer and a failed CodeRabbit read holds a required CodeRabbit review.

2 The loop inside this step

  1. Claude asks to merge
  2. The gate reads CI, the reviewers and CodeRabbit's threads
  3. Any no: back to that step
  4. All yes: on to approval

3 What decides each move

Every merge

  1. A required reviewer has not passed at this commit?the reviewer gateRefuseRe-run the review, or fix its findings.
  2. Unresolved CodeRabbit review threads?the reviewer gateRefuseResolve them first.
  3. A check failed or still running on this commit?the green-CI gateRefuseBack to Tests & CI.
  4. OtherwiseAllowOn to approval; the merge runs once it is given, pinned to the checked commit.

What if

Approvalapproval: you, or the chief in a fleet

Working alone, you decide when to merge: himmel does not require a GO for your own merges, except a change to a CI trust path, which needs a trust-reviewed GO. In a fleet, the worker reports READY and waits; the chief, itself a Claude session, checks it and writes a signed approval, the GO, for that one commit. A judge is added only when the change touches a trust path such as a guard, a gate or CI.

2 The loop inside this step

  1. READY, and wait
  2. The ready-check
  3. A trust path? A judge rules
  4. GO for this exact commit

3 What decides each move

Before READY

  1. CI red, or threads open?the CI reader in your projectBack to BuildSame exits as Tests & CI.
  2. Does the chief's ready-check fail? (head, CI, threads, trailers, ticket coverage)the readiness check from your himmel cloneRefuseThe worker fixes the one line that failed.
  3. Does the change touch a trust path (guards, gates, CI)?the approval writer from your himmel cloneAsk a judgeA separate judge session rules GO or NO-GO on that exact commit.
  4. OtherwiseAllowThe worker reports READY and waits. Waiting for approval is the only wait a worker is allowed.

What if

Writing the approval

  1. A worker trying to approve its own merge?the approval writer from your himmel cloneRefuseOnly the chief writes the approval file, signed for one pull request and one commit.
  2. No approval for this exact commit?the approval gate in your projectRefuseA new push needs a new approval.
  3. Is main itself red?the merge in your projectRefuseOnly a change that declares itself the fix goes through: a Fixes-main-red: line in a commit, or the chief's fix approval.
  4. OtherwiseAllowSquash merge; the worker wraps up and the chief closes its window.

What if

Ship and hand overin your project

The merge is pinned to the commit that was checked; the merge squashes it. The handover writes what was done and what is next, so the next session, or the next shift of the chief, starts where this one stopped.

2 The loop inside this step

  1. Merge the checked commit
  2. Write the handover
  3. The next session reads it
  4. Back to Plan

3 What decides each move

Handing over the chief

  1. Is the chief's context 45 % full?the chief start from your himmel cloneHand overIt starts its successor and writes a handoff note.
  2. Something of its own still running?the chief start from your himmel cloneRefuseIt stops its own tasks first.
  3. Is the relay delivered to every running worker? (the relay counts each worker it reached or printed a message for)the relay from your himmel cloneAllowThe old chief sends any printed message, then wraps; the new chief carries on from step 1.

What if

Planned: the hand-over will also carry the start, plan and design work still in flight (ideas being grilled, specs and plans that are not tickets yet), as short pointers only, each with a one-line status. The new chief opens one only when it picks that work up, so the hand-over stays small.
