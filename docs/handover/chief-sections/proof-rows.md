# Chief section — proof rows

Read on demand from `chief-sections/live-state.md`, when a `pool-disposition:` row is tagged `proof`.

A row tagged `proof` is dispatched to a `kind: proof` worker (gen-briefs). Read the latest `PROOF VERDICT` and the existing owed `validate-proof` record. CLOSE is a recommendation: the chief checks every actual DoD and Proof obligation, positive controls, three empty reads, current requirements, and applicable main/station/candidate ancestry. MET row counts cannot establish semantic completeness. Errors, skips, missing evidence, changed requirements or uncertain coverage remain KEEP/reconciliation. The user permits the chief to close fully proven tickets; proof workers remain read-only and never receive transition authority.

The chief writes a decision JSON with the record's exact `identity`, `verdict`, `rationale`, `coverage` and `controls` arrays of `{obligation,evidence}` citations, and an explicit `ancestry` judgement. Each citation quotes the bound artifact. The chief owns completeness and relevance of those citations; the mechanical check cannot certify either or grant permission. What the CLOSE check does mechanically, and nothing more: each citation's `obligation` is a phrase of the current DoD/Proof text (whitespace and case folded) and its `evidence` is a substring of the recorded artifact; the recorded artifact has no table cell or list item that starts with `NOT MET`, `OWED`, `SKIP…`, `ERROR(S)` or `FAIL…` (qualified forms such as `NOT MET — no RED` and `- NOT MET: …` included; prose that merely mentions a word is not a row); the evidence hash, requirement digest and identity are unchanged; no observation was omitted or truncated. Everything else (that every real obligation is cited, that a citation is relevant, that controls are meaningful) stays the chief's judgement. A CLOSE also requires a `matched` binding: the original `requirements-sha256 KEY=<digest>` line is read only from the generated brief above `## Results`, so a stamp in the worker's artifact or Results is untrusted (`requirements-stamp-untrusted`, binding stays unknown) and one that disagrees with the brief blocks (`requirements-stamp-conflict`). Use the normal absolute primary-checkout Jira CLI: `transition KEY Done --proof oN --proof-bucket DIR --proof-decision FILE`. It reads current requirements before and after the existing authorized transition, reads status back, and discharges through the existing owed writer only after confirmed Done. Normal version stamping applies; exit 3 retains actual Done plus an owned version-reconciliation step. Retry reads current Done without repeating the transition or reopening debt. A changed requirements/artifact identity requires a new proof record; comment-only changes do not. If the ticket is actually Done but its DoD/Proof changed between the pre-read and the post-read, the validation stays pending and one chief-owned `requirements-reconciliation` step (actual status, old and new requirement digests, due today) is persisted idempotently; the CLI exits 3 and a replay names that step instead of repeating or closing anything.

For KEEP, persist the exact next action, capable actor, due and wake before discharging validation. The JSON `next` object contains `actor` (`proof`, `worker`, `chief` or `operator`), `capability`, `text`, `due` (`YYYY-MM-DD`) and `wake`; use the same normal CLI with target `To Do`. The description's `Writes:`/`Staging:` or the partial PR's `Remaining:` line must also name the real next slice, so dispatcher routing follows requirements rather than a comment. A KEEP settles whether the ticket is In Progress (one `To Do` transition), already `To Do` (no transition is sent) or the first response was lost (the readback shows `To Do`): the proof path reads the status first and never transitions twice. Only `--proof` has this recovery; every other `jira transition`, `move` and MCP caller keeps the plain behavior, including an HTTP 4xx/5xx answer surfacing with its server message. A failed next-step append retains validation. While the newest validation of a ticket is open, the dispatcher lists its original proof-owned scope as the chief's `OWED` row, not a second proof run. Ordinary executable work owes a capable worker; only real human exceptions owe the operator. The check/settlement helper handles data and owed bookkeeping, never Jira mutations or authorization.

A row or an `OWED` line ending in `proof-staging=<needs>` goes to a proof worker only after each need is staged: the operator ones asked for in one plain message that names them, the chief ones done by the chief. The worker entry then carries `"staged": true`; gen-briefs refuses a `kind: proof` worker with needs without it and puts a `Staging needed before launch` block in the brief when it has it. The tag is per ticket, not per owed step: when an `OWED` line carries it, pick which owed step goes to a proof worker, and an owed step that is a repo write or a ticket to file is not one. A false need found in the DoD or Proof text is cleared with a `Staging: none` line in the ticket description (it never clears a need found in a next-step text; `"staged": true` dismisses that one, and the brief records it). A wall a proof worker hits that the ticket never named goes into the description as `Staging: <need>` (`gh-token`, `bypass-launch`, `read-secrets`, `guest-credential`, `go-code`, `throwaway-repo`, `operator-step`, `go-file`, or free text), a description edit in the same action as the KEEP, never in the KEEP comment. A need shown as `unknown` means an input could not be read: fix that input first; `"staged": true` on a worker that still lists one records your word that everything is in place, and the brief names the `unknown` beside it.
