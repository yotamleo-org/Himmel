# Chief section — proof rows

Read on demand from `chief-sections/live-state.md`, when a `pool-disposition:` row is tagged `proof`.

A row tagged `proof` is dispatched to a `kind: proof` worker (gen-briefs). Read the latest `PROOF VERDICT` and the existing owed `validate-proof` record. CLOSE is a recommendation: the chief checks every actual DoD and Proof obligation, positive controls, three empty reads, current requirements, and applicable main/station/candidate ancestry. MET row counts cannot establish semantic completeness. Errors, skips, missing evidence, changed requirements or uncertain coverage remain KEEP/reconciliation. The user permits the chief to close fully proven tickets; proof workers remain read-only and never receive transition authority.

The chief writes a decision JSON with the record's exact `identity`, `verdict`, `rationale`, `coverage` and `controls` arrays of `{obligation,evidence}` citations, and an explicit `ancestry` judgement. Each citation quotes the bound artifact. The chief owns completeness and relevance of those citations; the mechanical check cannot certify either or grant permission. What the CLOSE check does mechanically, and nothing more: each citation's `obligation` is a phrase of the current DoD/Proof text (whitespace and case folded) and its `evidence` is a substring of the recorded artifact; the recorded artifact has no actual result cell or list item that starts with `NOT MET`, `OWED`, `SKIP…`, `ERROR(S)` or `FAIL…` (qualified forms such as `NOT MET — no RED` and `- NOT MET: …` included; prose that merely mentions a word is not a row; a cell under an explicitly labeled `Expected` column in a supported Markdown table is an expected control input, so expected FAIL with actual MET does not block, while actual FAIL still does; in the table column its header calls Result, Status, Verdict, Outcome or State, when that column uses the proof vocabulary (at least one of its cells starts, in any letter case and through emphasis, with `MET`, `PASS`, `NOT MET`, `OWED`, `SKIP…`, `ERROR(S)`, `FAIL…`, `PENDING`, `WAITING`, `TBD`, `NOT YET DUE`, `AWAITING`, `NOT RUN` or `BLOCKED`), a row is MET only when its status is exactly `MET` (any letter case, emphasis and spaces ignored), so `MET (pending review)`, `MET, pending 24h`, `PASS`, `PASS (pending)`, `CONTROL RAN`, `Awaiting 24h`, `NOT RUN`, `BLOCKED`, a ticket status and an empty cell in that column are unmet, and the row's evidence text is never read for that: `| MET | … | pending count was 0 |` stays MET; a status column in which no cell starts with one of those words (a ticket-status column: `To Do`, `In Progress`, `Done`, `context`) is not a proof-row column and nothing in it refuses, but one `MET` among ticket statuses makes the column strict and refuses it, so name a ticket-status column something other than Status when it sits beside proof rows; a list item that starts with `PENDING`, `WAITING`, `TBD`, `NOT YET DUE`, `AWAITING`, `NOT RUN` or `BLOCKED` (any case, through emphasis) is unmet; a table with no such column, no header or a ragged row has no status position to read, so every cell of it is read for those words and `pending count was 0` there reads as not yet due; a table written without leading pipes is a table when a separator row follows its header); the evidence hash, requirement digest and identity are unchanged; no observation was omitted or truncated. Everything else (that every real obligation is cited, that a citation is relevant, that controls are meaningful) stays the chief's judgement. A CLOSE also requires a `matched` binding: the original `requirements-sha256 KEY=<digest>` line is read only from the generated brief above `## Results`, so a stamp in the worker's artifact or Results is untrusted (`requirements-stamp-untrusted`, binding stays unknown) and one that disagrees with the brief blocks (`requirements-stamp-conflict`). Use the normal absolute primary-checkout Jira CLI: `transition KEY Done --proof oN --proof-bucket DIR --proof-decision FILE`. It reads current requirements before and after the existing authorized transition, reads status back, and discharges through the existing owed writer only after confirmed Done. Normal version stamping applies; exit 3 retains actual Done plus an owned version-reconciliation step. Retry reads current Done without repeating the transition or reopening debt. A changed requirements/artifact identity requires a new proof record; comment-only changes do not. If the ticket is actually Done but its DoD/Proof changed between the pre-read and the post-read, the validation stays pending and one chief-owned `requirements-reconciliation` step (actual status, old and new requirement digests, due today) is persisted idempotently; the CLI exits 3 and a replay names that step instead of repeating or closing anything.

What else refuses a CLOSE, with the message it gives and what you do about it (`--check` and a settle on a ticket that is not Done refuse and write nothing; a KEEP is never asked):
- **Another open step of the ticket** (an open `worker`, `chief` or `operator` step of the key, in any key case; a proof step and a requirements or version reconciliation do not count): `open code/chief step oN (worker: <its text>) remains open; if it is finished, close it with `bash <kit>/owe.sh close --bucket <dir> --id oN --key KEY`; if work really remains, record a KEEP decision instead`. Nothing closes such a step for you, so the KEEP, worker finishes, new proof, CLOSE cycle needs you to run that `owe.sh close` for the finished step first; if the work is not finished, KEEP.
- **A not-yet-due observation** (`PENDING`, `WAITING`, `TBD` or `NOT YET DUE` in a row's status, above): `unmet/skipped/error proof row`. Wait for the window and have the proof worker record the result, or KEEP with the due and the wake.
- **Open code work or an owed chief or operator line in the ticket's live pull-request remainder** (read from the status log and `gh pr view` through the dispatcher's own seams, the grammar and the newest partial PR winning as the dispatcher has them, within one 90 s budget; it differs from the dispatcher on purpose in two ways: a unit that names a path the dispatcher's own pattern knows is code whatever words follow, including a path it only runs, and what the dispatcher would read as nothing, a warning from the log helper or a merge row with no PR number, is a read that failed; a remainder that names no path and says it writes no code, `owed -> proof` lines and a hand-off do not count): `live pull-request remainder blocks the CLOSE: PR #77 Remaining: <text>; KEEP required` (an owed line names its text; a body with no remainder says `PR #77 records no remainder`). Build or finish it and let its PR say so (or edit the PR body to the truth, `deferred -> <KEY>` for a hand-off), or KEEP naming the next slice.
- **A remainder that cannot be read**: `live pull-request remainder unreadable: PR #77 body unreadable (gh exit 1)` or `status log <path> unreadable (<why>)`, then `; the CLOSE is refused until it can be read` (a warning of the log helper reads `status log <path> unreadable (the log helper warned: ... PR 77 unreadable on GitHub ...)`, a merge row with no PR number `status log <path> unreadable (merge row for KEY has no PR number)`, a read past the budget `PR #77 body unreadable (gh ran past the read budget)`). Nothing was written; fix the read (gh, the log, the row) and decide again. A missing status log is no partial merge.
- **Something opens after the check** (the Jira CLI moved the ticket to Done, then the settle finds an open step or a remainder): the settle writes ONE step for you, `Reconcile close: KEY is Done but <what> still blocks the CLOSE; validation oN stays pending. Clear it first (build or finish it, close what is finished, or edit the pull request to the truth), then close this step, then record the decision again; …`, discharges nothing, and the CLI prints the names and `remainder reconciliation oM` and exits 3. A replay writes no second step while that step is open. If you close it while the blocker is still open, the next settle writes a NEW open step that begins `Earlier reconciliation step oM was closed with the blockers still open.`: there is always one open owner. If the settle itself fails after the move, the CLI prints `FAIL KEY is now Done in Jira but validation oN is NOT settled: <why>`, `Nothing was moved back. Run it again: <the exact command>` and exits 1; fix the cause and run that command.
- A proof-owned step created after the evidence was recorded does not block (this handoff discharges only the proof steps it bound): list the key's open rows with `owe.sh list --bucket <dir>` before you cite coverage.

For KEEP, persist the exact next action, capable actor, due and wake before discharging validation. The JSON `next` object contains `actor` (`proof`, `worker`, `chief` or `operator`), `capability`, `text`, `due` (`YYYY-MM-DD`) and `wake`; use the same normal CLI with target `To Do`. The description's `Writes:`/`Staging:` or the partial PR's `Remaining:` line must also name the real next slice, so dispatcher routing follows requirements rather than a comment. A KEEP settles whether the ticket is In Progress (one `To Do` transition), already `To Do` (no transition is sent) or the first response was lost (the readback shows `To Do`): the proof path reads the status first and never transitions twice. Only `--proof` has this recovery; every other `jira transition`, `move` and MCP caller keeps the plain behavior, including an HTTP 4xx/5xx answer surfacing with its server message. A failed next-step append retains validation. While the newest validation of a ticket is open, the dispatcher lists its original proof-owned scope as the chief's `OWED` row, not a second proof run. Ordinary executable work owes a capable worker; only real human exceptions owe the operator. The check/settlement helper handles data and owed bookkeeping, never Jira mutations or authorization.

A row or an `OWED` line ending in `proof-staging=<needs>` goes to a proof worker only after each need is staged: the operator ones asked for in one plain message that names them, the chief ones done by the chief. The worker entry then carries `"staged": true`; gen-briefs refuses a `kind: proof` worker with needs without it and puts a `Staging needed before launch` block in the brief when it has it. The tag is per ticket, not per owed step: when an `OWED` line carries it, pick which owed step goes to a proof worker, and an owed step that is a repo write or a ticket to file is not one. A false need found in the DoD or Proof text is cleared with a `Staging: none` line in the ticket description (it never clears a need found in a next-step text; `"staged": true` dismisses that one, and the brief records it). A wall a proof worker hits that the ticket never named goes into the description as `Staging: <need>` (`gh-token`, `bypass-launch`, `read-secrets`, `guest-credential`, `go-code`, `throwaway-repo`, `operator-step`, `go-file`, or free text), a description edit in the same action as the KEEP, never in the KEEP comment. A need shown as `unknown` means an input could not be read: fix that input first; `"staged": true` on a worker that still lists one records your word that everything is in place, and the brief names the `unknown` beside it.
