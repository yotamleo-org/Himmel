# Graph publish cadence — reference

> The `HIMMEL-GraphPublish-Himmel` scheduler task, armed via
> `scripts/luna/graphmap-cadence.sh` alongside its four sibling tasks
> ([`docs/tooling-catalog.md`](../tooling-catalog.md) covers those). This page
> is the fuller reference for the fifth: `scripts/graphify/graph-cadence.sh`,
> its ledger, and its failure surfacing.

## Why this exists

himmel's own graphify graph (`graphify-out/graph.json`) is heavily used —
139 of 143 sessions on the day this was written, via the MCP tools or the
CLI — but nothing refreshed or published it on a schedule, so it silently
rotted (the shipped graph sat 36 commits behind `origin/main` when this was
written). Because refreshing was lean-invoke only
(`graph-refresh`/`graph-publish` skills, operator-triggered), the graph got
regenerated by hand and committed **straight to `main`** with a bare,
ticketless subject — bypassing the worktree/PR workflow every other change
in this repo goes through (`d05ef8ca` "update graphify", `913073df` ".",
`378c21f9`/`310646da` "graphify update"). `graph-cadence.sh` exists to remove
the reason that happened: an unattended runner that measures staleness,
refreshes, publishes via a PR, and auto-merges it through the sanctioned
script.

## What it does, in order

1. `git fetch origin` — safe: fetch only updates remote-tracking refs, never
   the checked-out branch or working tree, so it never disturbs a live
   session working in the primary checkout.
2. Reads `built_at_commit` out of the **shipped** `graphify-out/graph.json`
   (`origin/main`'s committed blob via `git show`, not whatever happens to be
   on disk).
3. Measures staleness as `git rev-list --count <built_at_commit>..origin/
   main` — **not** `--merges`. himmel squash-merges every PR, so
   `--count --merges` always returns 0 while the true distance is the real
   number.
4. Below `--threshold`: `action=skipped`, one ledger row, exit 0.
   **No tracked graph (the steady state):** `origin/main` no longer carries
   `graphify-out/graph.json`, so there is nothing to measure or publish. Without
   `--semantic` the run then exits right here — `action=skipped`, no pipeline lock,
   no worktree sync, **no `ast-update.sh` rebuild**. The only
   rebuild of the himmel AST graph per cycle is the hourly
   `HIMMEL-GraphMapAst-Himmel` run into the primary checkout's `graphify-out/`,
   which is what the graph workers and the session-start advisory read; a rebuild
   in this step's worktree would feed nothing. `--semantic` keeps the rebuild (the
   semantic step builds on it and promotes it into the primary), and an
   unreadable `graph.json` object (corrupt clone) still falls through and fails
   closed (rc 3) rather than hiding behind the skip.
5. At/above threshold (a tracked graph only): `ast-update.sh` (the free, AST-only structural
   refresh), `graph-publish.sh` (open/refresh the publish PR), then
   `merge-on-green.sh` (`ARMAUTOMERGE=1`, the sanctioned auto-merge
   script) — all three against a **dedicated worktree**, never the
   primary checkout (see below). A failing refresh short-circuits the
   remaining steps (see `graph-cadence.sh`'s own header for why this diverges
   from `ggs-cadence.sh`'s convention of running every step regardless).

## Where it runs — the dedicated worktree

`graph-publish.sh` does `git checkout -B chore/graph-publish-<corpus> ...`
in whatever repo it is invoked from, and `ast-update.sh` writes tracked
`graphify-out/*` files into whatever corpus root it is given. Firing either
against the primary checkout from cron would switch the branch of a repo
live agent sessions are working in and leave its tracked `graphify-out/`
dirty — exactly the temptation that produced the manual bare commits this
ticket exists to stop.

So every mutating step runs inside `~/.claude/graph-cadence/<corpus-slug>`
(himmel → `himmel`), created on demand via `git worktree add` off the
primary and force-synced to `origin/main` (`checkout -B` + `reset --hard` +
`clean -fdx`) at the start of every run. A worktree has its own HEAD/index
and never touches the primary's checked-out branch or working tree — proven
by `test-graph-cadence.sh`'s own primary-untouched assertion (branch, HEAD,
`git status --porcelain`, and `git worktree list`'s row for the primary
itself, all asserted byte-identical before/after a full run).

**Never `/tmp`**: a cleanup sweep reaping a live worktree registration out
from under git's `.git/worktrees/<name>` bookkeeping leaves the primary
checkout's `git worktree list` pointing at a hole. `~/.claude/graph-cadence/`
follows the same persistent-runner-home convention every sibling cadence in
this repo already uses (`graphmap-cadence.sh`'s own `~/.claude/graphmap-
cadence`, `ggs-cadence.sh`'s `~/.claude/graphify-cadence`).

The worktree's **dirname must equal the corpus slug**: `graph-publish.sh`
derives its PR branch name from `basename(git rev-parse --show-toplevel)`,
with no `--corpus-name` override. `graph-cadence.sh` names the worktree
accordingly *for exactly this reason*, so the branch name it predicts (and
hands to `merge-on-green.sh` as an explicit selector — never the default
"current branch", which would resolve to the worktree's own housekeeping
branch after `graph-publish.sh`'s `restore_branch` puts it back) matches
what `graph-publish.sh` actually creates.

## Arm / inspect / remove

Same three verbs as every sibling cadence, via the shared
`graphmap-cadence.sh` entry point — there is no separate arm command for
this step:

```bash
bash scripts/luna/graphmap-cadence.sh arm        # registers the himmel tasks (the Luna tasks are off by default)
bash scripts/luna/graphmap-cadence.sh arm --with-publish  # also registers the publish task (opt-in)
bash scripts/luna/graphmap-cadence.sh arm --force  # replace an existing himmel arm
bash scripts/luna/graphmap-cadence.sh arm --luna-only  # opt in to the Luna tasks (decision 449: off until graphify beats qmd on Luna)
bash scripts/luna/graphmap-cadence.sh status     # per-task ARMED/not-armed + run log
bash scripts/luna/graphmap-cadence.sh disarm     # removes every task; disarm --luna-only removes the Luna ones alone
```

The Luna graph tasks (`HIMMEL-GraphMap-Luna`, `HIMMEL-GraphMapAst-Luna`,
`HIMMEL-GraphSemantic-Luna`) are off by default: a bare `arm`
neither adds nor replaces them, a fresh install registers none (so doctor C24
expects none), and `himmel-update`'s `arm --rewrite-armed` only rewrites runners
that already exist, so it can never re-arm a disarmed Luna task.

The publish task is opt-in: `arm` registers `HIMMEL-GraphPublish-Himmel`
only with `--with-publish`. It is grouped with the free structural (AST) pair for
`--ast-only` purposes: it needs no backend credential, so
`--ast-only` arms/replaces it too, alongside the himmel AST task, while leaving the
himmel semantic task untouched. Default schedule: **every 6 hours**,
anchored at `:35` past (`35 */6 * * *`) — 20 minutes clear of `HIMMEL-GraphMapAst-Himmel`'s
own `:15`-past hourly fire, wider than the AST pair's own 10-minute mutual
stagger, because this step is not free-and-instant like the AST pair: with a
tracked graph or `--semantic` it can run `ast-update.sh`, open/refresh a PR, and
drive `merge-on-green.sh`'s own `check-ci` watch, all in one fire (without
either it skips at once and rebuilds nothing — the hourly AST pair already
built the graph). Both steps would otherwise contend for
`ast-update.sh`'s promote lock (skip-not-wait, so a collision is
a skipped-and-retried refresh next fire, not a failure — the wider offset
just makes that the exception rather than the rule). The post-merge tick below
fires every five minutes, so it lands on `:15` and `:35` too: its graph half
takes the same lock, treats a busy one (rc 4) as a skip and retries on its next
tick, so no offset is kept clear for it.

Two fires of this step itself are serialized by `graph-cadence.sh`'s own
pipeline lock (`<worktree>.lock`), because each run `reset --hard` +
`clean -fdx`es the same worktree. `mkdir` is the whole protocol (following `scripts/luna/qmd-cadence.sh`, where three rounds of automatic
stale-lock takeover each produced the next race). A run proceeds only if its
own `mkdir` succeeded, and nothing ever removes a lock it did not create: the
exit trap removes the run's own instance only, by owner token. The lock
records the holder's pid, host and a `heartbeat` re-stamped every 30s — for
detection only. A contender that finds a live holder (pid alive on this host,
or a heartbeat under 600s old from another host) skips, `action=skipped`,
rc 0. A contender that finds a dead holder never takes the lock over: it
refuses loudly — `action=failed`, rc 3, naming the lock path, the holder pid
("stale: holder pid N dead") and its age — and so does every later fire until
an operator removes `<worktree>.lock`. `himmel-doctor` C33 surfaces that
failed row. A run re-checks its owner token right before its first
destructive git command. A refreshed graph lands only through a `chore/graph-publish-<slug>`
PR merged on green — never a direct push to `main` (asserted in
`test-graph-cadence.sh`).

## The post-merge tick

`scripts/luna/post-merge-refresh.sh` is a separate five-minute tick that refreshes the code graph (and, in `both` mode, the himmel keyword index) after merges settle, with no paid call. Nothing arms it on its own; an operator arms it:

```bash
bash scripts/luna/graphmap-cadence.sh post-merge graph   # code graph only
bash scripts/luna/graphmap-cadence.sh post-merge both    # code graph and keyword index
bash scripts/luna/graphmap-cadence.sh post-merge off     # row, runner and registrations removed
```

- **One row, nothing else.** The verb writes only `HIMMEL-PostMergeRefresh` at `*/5 * * * *` and every other crontab row back unchanged. The row sits outside the arm family: `arm` and `arm --force` leave it alone, a full `disarm` removes it with its runner and registrations, `disarm --luna-only` leaves it, and `status` lists it with its mode.
- **A bare runner.** `~/.claude/graphmap-cadence/post-merge-refresh.sh` appends to `post-merge-refresh.log` beside it (checked before each fire and moved to `.prev` once it passes 1 MB, so the live log can pass 1 MB by one fire's output), writes no flow rows and never clears an alert (the tick clears `post-merge-tick` itself on a clean pass). When the tick exits non-zero it raises `post-merge-tick` through `cadence-alert.sh`.
- **What cron does not carry.** The runner pins at arm time the `PATH` directories of `graphify`, `bun`, `qmd` and `node`, so the tick finds them, and runs from its own directory: qmd walks up from the working directory for a project-local `.qmd/index.yml`, and the tick sets none. Arming refuses when `graphify` is not an absolute executable on `PATH`.
- **The mode** is one generated line in the runner, `# himmel-post-merge-mode: graph` (or `both`). `arm --rewrite-armed` reads it, rewrites the runner only when one exists, and refuses with exit 2, rewriting nothing, when the line is absent, repeated or in any other form. It never adds the tick.
- **Registration.** The task `HIMMEL-PostMergeRefresh` and the flows `post-merge-graph` (and `post-merge-keyword` in `both`) are registered with `cadence_seconds` 604800 and `stall_deadline_seconds` 3600. A stall deadline an operator already set on a flow is kept.
- **Lock alerts name the holder.** The 30-minute lock alert gives the pid of the live holder, since lock liveness is by pid alone.

## The ledger

Two ledgers, both written every run:

1. **`<handover-root>/.graph-cadence/ledger.jsonl`** — this step's own,
   resolved via `scripts/lib/handover-path.sh`'s `handover_root` (never a
   literal path). One JSON line per run:

   ```json
   {"ts":"2026-09-06T14:34:57Z","head":"<origin/main sha>","graph_head":"<built_at_commit>","merges_behind":21,"lag_s":5400,"action":"merged","pr":"https://github.com/.../pull/42","duration_s":36,"error":null}
   ```

   `graph_head` is the build commit of the graph, `merges_behind` how many
   commits `origin/main` is ahead of it, and `lag_s` how many seconds apart the
   two commits are (null when either commit cannot be read). A
   `published-channel` row sets all three from the commit the publish carried;
   see [How far behind the published graph is](#how-far-behind-the-published-graph-is).

   `action` is one of `skipped | failed | refreshed | published | published-channel | merged` —
   `published-channel` means the run pushed its graph to the `graph-data`
   branch (see [Sharing the graph](#sharing-the-graph--the-graph-data-branch)).
   For the other actions,
   see `graph-cadence.sh`'s header for the full classification (in short:
   `published`, not `failed`, ONLY when `merge-on-green.sh` exits with a
   documented time-resolving deferral — check-ci gate not green, or an
   indeterminate/retryable merge attempt (its own exit codes 14/15). Any
   OTHER non-zero `merge-on-green.sh` exit — a missing tool, an unwritable
   audit sink, a misconfigured base/privacy binding — is `failed`, not
   `published`: not every non-landing merge is a benign "not yet", and a
   permanently broken merge step must not read as healthy forever).

2. **The standard flow-run ledger** (`~/.himmel/flow-runs.jsonl` by default,
   `scripts/lib/flow-run-ledger.sh`) — a `start`/`end` row pair under flow
   name `graph-publish-himmel`, the same mechanism every other cadence in
   this repo writes, so the existing cadence-audit/staleness tooling is not
   blind to this step.

**`HANDOVER_DIR` is required, not optional**: cron gives
no login shell, so `HANDOVER_DIR` is exactly the variable that goes missing
there. If it is unset, `graph-cadence.sh` refuses **loudly** — non-zero exit,
a clear stderr message naming the variable, a line in the runner's own
per-fire log, and a flow-run-ledger row with `outcome:"error"` — rather than
let `handover_root_ensure` silently `mkdir -p` himmel's own `handovers/`
Mode-A stub and write the cadence ledger straight into the git repo it
publishes. Set it via `/handover-setup`, or see
[`docs/internals/handover-system.md`](handover-system.md).

## The standing ticket

Every publish PR's commit subject carries the standing ticket's key in brackets — this repo's CI
commit-range gate requires a ticket ID on every commit, and the PR's subject
used to carry none at all (plausibly why the manual bypass was reached for
in the first place; see "Why this exists" above). `graph-publish.sh --ticket
<ID>` (default: the key in the script, or `$GRAPH_PUBLISH_TICKET`) lets the standing
ticket change without editing code.

## The threshold, and its trade-off

Default **15** commits behind. Justified against the measured numbers: the
shipped graph was 36 commits behind `origin/main` when this was written,
with the operator refreshing by hand at irregular multi-day intervals. This
cadence fires up to 4×/day (every 6h). A threshold of 3 (this repo's typical
single-PR commit count) would open a publish PR on almost every run —
constant PR churn for a marginal freshness gain. 15 sits below half of the
measured 36-commit gap: it fires immediately at that staleness, and in
steady state bounds the graph's staleness to roughly "at most one busy day's
worth of merged PRs" rather than the previous unbounded, hand-triggered-only
gap, while still going quiet on days with only a handful of merges.

This is a starting point, not a measured optimum. Retune it by editing
`THRESHOLD=15` in `graph-cadence.sh` itself — the emitted runner's payload is
`bash graph-cadence.sh --corpus-root <path>`, with **no `--threshold` baked
in**, so it always falls through to the script's own current default. A
default change therefore takes effect on the **very next scheduled fire**,
with no re-arm needed. (`--threshold <N>` still exists for an ad-hoc manual
run against a different value — it just isn't what the armed cadence uses.)

## The `--semantic` step: which exit codes alert

With `--semantic`, `graph-cadence.sh` runs `semantic-update.sh` on the
dedicated worktree and classifies its exit code. The backend is
`GRAPH_CADENCE_SEMANTIC_BACKEND`: `claude-cli` (default, Sonnet, gated on the subscription usage budget),
`claude-api` (API credit through the API lane; needs `HIMMEL_API_LANE=on` and `HIMMEL_API_ACCOUNT`, refuses rc 1
otherwise; with `GRAPHIFY_API_BATCH=0` a failed chunk call follows the [API lane's fallback rule](api-lane.md), while the default batch mode submits through the Message Batches API and has no alert or fallback) or `ollama` (opt-in, local, needs a GPU); `api` and `cli` are
aliases, resolved by `scripts/lib/llm-backend.sh`. Any other value refuses (rc 1) before any work.

| rc | meaning | cadence result |
|---|---|---|
| 0 | ok, no change since the last pass (no-op), or on `claude-api` a batch submitted or still pending (graph untouched) | green; clears the `graph-semantic-<slug>` alert |
| 3 | subscription usage budget at/over threshold, nothing touched (claude-cli only; the ollama path skips the usage budget check) | benign skip: green, no alert, an existing alert is left standing |
| 4 | promote lock held by another graph refresh, nothing touched | benign skip: green, no alert, an existing alert is left standing |
| 5 | one or more semantic chunks failed (the good chunks merged, the failed files stay unstamped) | alerts (`semantic-update-rc-5`), `action=failed`, rc 3 |
| 1, 2, other | usage/IO, fence deny, batch submit failure, graphify or merge failure | alerts (`semantic-update-rc-<n>`), `action=failed`, rc 3 |

On `claude-api`, `semantic-update.sh` passes graphify `--token-budget` derived from `GRAPHIFY_API_CALL_BUDGET_USD`
(120000 tokens per USD, capped at graphify's 60000), so a chunk fits one lane call; the default 0.25 USD gives
30000. The estimate line prints the cap, the chunk size and the expected per-chunk cost.

`claude-api` extraction runs through the Message Batches API at half price (`GRAPHIFY_API_BATCH=0` keeps the
synchronous path). A first pass records the chunk prompts and submits one batch; the graph and manifest stay
untouched and `graphify-out/semantic-batch/batch.json` holds the batch id. Each later fire polls that batch instead
of resubmitting; once it has ended, the answers are replayed through graphify and merged like a synchronous run.
When `HIMMEL_API_ACCOUNT=auto`, a credit-exhausted submit moves on to the next account of the pick list, each account
at most once per pass, and only a credit-exhausted answer moves on; `A`, `B` or `C` pins one (no budget gate). `GRAPHIFY_API_BATCH=0` refuses (rc 2) while a batch is pending, so a synchronous merge cannot be
overwritten by an older batch later.
The ledger row carries `batch_id`, `batch_state` (`submitted`, `pending`, `merged`), `batch_requests` and
`batch_cost_usd`; cost is null until the batch is merged.

A skip is not a recovery, so it never clears a standing alert; only a clean rc 0
does. On the local ollama path `semantic-update.sh` exports the placeholder
`OLLAMA_API_KEY=ollama` (a caller-set key wins) so graphify's "no OLLAMA_API_KEY"
warning stays out of the extract log; that is only done after the loopback and
non-cloud-model checks, so the cloud path keeps its warning and any real auth
error. `refresh-graph-map.sh --backend ollama` likewise defaults to
`--max-concurrency 1` for a local endpoint (the model holds the whole GPU); an
explicit `GRAPHIFY_MAX_CONCURRENCY` wins, and an ollama-cloud model keeps 6.

## Where failures show up

- **The armed task's own run log** — `graphmap-cadence.sh status` surfaces
  it: `~/.claude/graphmap-cadence/graphmap-publish-himmel.log` (rotated to
  `.log.prev` each fire by the cron wrapper `graphmap-cadence.sh`
  itself emits). This captures `graph-cadence.sh`'s **complete** stdout +
  stderr for the fire — fetch, `ast-update.sh`, `graph-publish.sh`,
  `merge-on-green.sh`, all of it — and is the log to check first during an
  incident.
  `graph-cadence.sh` also carries its own internal `LOG_FILE`
  (`~/.claude/graph-cadence/<corpus-slug>.log`, e.g. `himmel.log`) — but that
  path is written ONLY by the `HANDOVER_DIR`-unset refusal (a narrow,
  pre-worktree failure mode reached before the run log above even exists);
  it is not rotated and is not where a normal run's output lands. Don't
  confuse the two.
- **This step's own ledger** (`<handover-root>/.graph-cadence/ledger.jsonl`)
  — `action:"failed"` plus the real error text. A failed *append* to this
  file is itself a hard failure (exit 4, distinct from every other code) —
  see `graph-cadence.sh`'s own exit-code table: the ledger IS the report, so
  a run that could not record itself is never read as a quiet success.
- **The standard flow-run ledger** — an `end` row with `outcome:"error"`.
- **`himmel-doctor.sh`**: a `C33-graph-stale` row (`check_c33_graph_stale`;
  the ID may have been renumbered again by the time you read this — check
  that function's own header) reads the ledger's last row and WARNs (never
  FAILs — an unpublished graph degrades query quality, it never breaks the
  harness) when the last run is older than 3× the armed interval, the last
  recorded action is `failed`, or the row's action is unrecognized/
  undetermined (a missing `jq`, or an unparseable row — "cannot tell" must
  never render as "healthy").

## Sharing the graph — the graph-data branch

One station pays for the semantic pass. Every other station gets the result
for free.

**Publishing (the one station).** A `--semantic` run that promotes its graph
then runs `scripts/graphify/publish-graph-channel.sh`. The script publishes
four files to the `graph-data` branch: `graph.json`, `GRAPH_REPORT.md`,
`manifest.json`, and a one-line `built_at_commit`. Nothing else is
published: no `graph.html`, no cache, no run log. The branch holds one commit
with no parent, and each publish replaces it (`--force-with-lease`). The
ledger row reads `action=published-channel`.

The script refuses to publish when:

- one of the files is missing;
- `graph.json` names no exact commit;
- the graph has no semantic layer, meaning `semantic-manifest.json` is
  missing or lists no files.

**The scan.** Before it pushes, the script scans the exact bytes it is about
to push, in two ways:

- gitleaks, with the repo's `.gitleaks.toml`;
- a pattern for host paths, such as home folders, user-profile folders and
  session scratch folders.

Any hit blocks the push. If gitleaks is missing or errors, the push is
blocked too. A blocked push fails the run with `action=failed` and exit 3.

**The alert.** Every refusal raises a cadence alert on the worker
`graph-channel-publish`. The alert and the ledger name the file and the
rule, for example `file=graph.json rule=host-path`, and never the matched
text. The next clean publish clears the alert.

**Fetching (every other station).** `himmel-update.sh` runs `sync_graph`
after `sync_graphify`, and its status table shows a `graph` row. It fetches
`graph-data` and installs the graph only when all of these hold:

- the graph's build commit is in this checkout's history;
- the build commit is at most 150 commits behind `HEAD`
  (`HIMMEL_UPDATE_GRAPH_MAX_BEHIND` changes the limit);
- the fetched bytes contain no host path;
- the `built_at_commit` file matches the commit inside `graph.json`.

The files are staged in a temp folder, then moved into `graphify-out/`
with one rename per file. The fetch then stamps the semantic manifest
(`semantic-update.sh --seed-manifest`, with no model call) from the docs as
they stood at the build commit. The next semantic pass then has nothing left
to do, except for docs that changed after that commit.

If the graph is stale, off this checkout's history, missing or tampered
with, the station stays AST-only and `graphify-out/` is not touched.
`--check` reports what it would fetch and writes nothing. A station with
`graphify.semantic_api_ok` set to true in `~/.himmel/config.json` is the
publisher, so it never fetches.

### How far behind the published graph is

Every `published-channel` row records the lag at the moment of the publish
(`graph_head`, `merges_behind`, `lag_s`). A publish that lands carries a graph
that is already a few commits old, and the next publish is hours away, so the
lag adopters see at their own update is higher than any one row. To measure
that, replay it:

```sh
python3 scripts/graphify/graph-lag-report.py --ledger <handover-root>/.graph-cadence/ledger.jsonl --repo <himmel checkout> --days 14
```

The report needs no network and writes nothing. For each hour of the window the
published graph is the latest `published-channel` row at or before it; failed
and skipped fires leave it where it was, so a run of them shows as a growing
gap. The lag at an hour is the number of commits on `origin/main` (else `main`)
made by then that the build commit does not contain. It prints:

- `p50`, `p90` and `max` over the window's hours;
- the hours over the limit adopters refuse the graph at, read from
  `GRAPH_MAX_BEHIND` in `scripts/himmel-update.sh`;
- the hours over 40 and over 100, and the target: `p90` at most 40 and `max`
  at most 100.

Hours before the first `published-channel` row have no baseline
(`no-baseline-hours`), and hours after a publish whose build commit the
checkout cannot read, or that names none, are `unknown-hours`: the report leaves
both out of the figures and never reads them as an older graph's lag.

The target reads `HOLDS` or `BREACHED` only when every hour of the window has a
figure. Otherwise it reads `INCOMPLETE covered=<n>/<total>` whatever the
figures say, so 14 days of `--days` over a ledger that is 2 hours old is never a
passed window. When no hour has a figure (an empty ledger, no
`published-channel` row, or only unreadable ones) the report exits 3; exit 2 is
bad input. It also prints the commit time of the ref it measured against, and a
`WARN` when that is more than 6 hours older than the window's end, since a stale
checkout makes the lag read too low.
`--now` ends the window at a fixed time instead of the present.

## Luna graph freshness

The luna vault graph is rebuilt AST-only nightly (`HIMMEL-GraphMapAst-Luna`), so
its markdown only gets LLM extraction from a separate job:
`bash scripts/luna/graphmap-cadence.sh arm --luna-only --ast-only --with-luna-semantic --api-account A`
(account B or C also works; the flag is required and `auto` is refused) adds `HIMMEL-GraphSemantic-Luna` (cron, `50 */2`), which runs `semantic-update.sh
--name luna --corpus-class luna-personal --backend claude-api` against the same
external out dir the AST job writes (an absolute `GRAPHIFY_OUT`), capped at 20
changed files and 2 USD per fire. It arms PAUSED (`semantic-luna.paused` beside
the runner; `rm` it to resume) and needs a `semantic-manifest.json` baseline
(`semantic-update.sh --seed-manifest`) first, or the whole vault counts as
changed. Check freshness in `<out>/semantic-runs.jsonl`: a luna graph with no
claude-api row there has never had semantic extraction.

## Adding a second corpus (out of scope for v1)

himmel is the only corpus wired, and `--corpus-root` currently **refuses**
any value that doesn't canonicalize to the resolved primary checkout
(rc=1) — it is not a real multi-corpus switch today (PR-B panel r1,
codex-3): fetch, the shipped-graph read, staleness measurement, and the
dedicated worktree's *source* all still target `$HIMMEL_ROOT` unconditionally
inside the script, regardless of what `--corpus-root` is given. A flag that
looked like it worked and silently operated on the wrong repo was judged
worse than no flag, so it refuses instead.

To add a real second corpus: make those four internal uses of `$HIMMEL_ROOT`
(fetch, shipped-graph read, staleness measurement, worktree source) key off
`$CORPUS_ROOT` instead wherever the two can legitimately differ, verify that
end-to-end against a fixture repo (mirroring `test-graph-cadence.sh`'s own
hermetic pattern), THEN drop the refusal above; give the new corpus its own
worktree slug (`~/.claude/graph-cadence/<slug>`, matching that corpus's own
directory basename so `graph-publish.sh`'s branch-name derivation still lines
up) and its own scheduler task name (following the
`HIMMEL-GraphPublish-<Name>` convention).
