himmel · for Claude Code

Ship more with Claude Code, and keep every change reviewable.

himmel puts Claude Code's work on a delivery graph. Each change is built in its own worktree, checked three ways at once, reviewed (by a second model too, once you add one) and merged through one gate. The guardrails apply to every session, including the ones you are not watching. For developers on Linux or macOS who use git.

  • One road for every changeEach change gets its own worktree, then passes the tests, a review and one merge gate. No step can be skipped. When a check fails, the change goes back with the reason, so main only gets work that passed.How a change ships
  • Guardrails that holdEdits and commits on main, pushes to main, reads of secret files, rm -rf, hard resets and force pushes are refused before they run.Level 1 · in your project
  • Cost you can seeHeavy work checks your remaining Claude usage first, and the fleet records the cost of what it merges.Level 5

himmel is built this way. Over 2,000 pull requests merged on its own main in 30 days (October 2026). See the graph they went through

A new project, shipping fast. The rules that keep it fast.
  • Guards aimed at real damage. Each guard targets a move that can hurt a project, and is replayed against real commands before it ships, so it stops what matters and lets the rest through.
  • Long tracks keep their pace. Each session keeps its context small, so its answers stay sharp. When it fills, a worker hands off at a set point and the chief passes the shift to a successor, with everything written down, so a long track never starts over.
  • Every merge is earned. A change merges through one gate only: CI green at its exact commit, every review point decided, and an approval signed for that commit.
  • Cleanup keeps every session fast. Stale worktrees and open tickets slow down each session that has to step around them, so finished worktrees are cleared and tickets close when their change merges.

What it is, and how you stay in control

himmel adds a delivery process to Claude Code. You decide how much of it runs, and where.

Question 1What is it?A delivery process for Claude Code: worktrees, git gates, a review (by a second model too, once you add one) and one merge gate, with guardrails that hold.

Small scripts fire automatically and refuse risky actions (edits and commits on your main branch, reads of your secret files, pushes to main), so the rules hold even when nobody remembers them.

Five words you will see

  • Hook: a script Claude Code runs before or after a tool; it can refuse the action.
  • Gate: a check that must pass before a commit, push or merge.
  • Worktree: a second working folder on its own branch, sharing the repo's history.
  • Handover: a written note a later session resumes from.
  • Sector: one region of your project's sky: a stable area of the work, the "where" of a ticket, so each area's progress shows on its own.

Every other term is in the glossary.

Who it is for

Developers who use git and a terminal. Linux and macOS are supported.

Question 2Who is in control?You are. You choose what runs, you see the plan before anything is written, and you can switch any part off.
  • You choose the starting point. A starter install for one project, or more: a second brain, a second reviewer, a fleet. Install profiles
  • You see the plan first. The installer lists everything it would add or change, and asks before it writes a thing.
  • Nothing runs on a schedule until you arm it, one job at a time.
  • Every guardrail has an off switch for one session, when you mean it.
  • One command takes it all back out. How
Question 3What changes on my machine, and how do I undo it?Files and settings in the project you install into, a few in your home folder, all recorded; one command takes them back out.

Read these four first

  1. Helper scripts are copied into scripts/. A file with the same name is replaced only after himmel has backed it up, and uninstall restores it. If the backup cannot be made, the file is left alone and the install says not replaced … (cannot back up the existing file; left untouched). The preview lists every file it would replace.
  2. Your statusLine is replaced in .claude/settings.json, and ~/.claude/plugins/claude-hud/config.json is rewritten. Both old values are backed up and uninstall restores them.
  3. Commits and pushes to main are refused at once. If your project has no .pre-commit-config.yaml, the install places himmel's own git gates. They refuse a commit on main, a direct push to main, and a commit message without a conventional type and a ticket reference such as #1. No tracker? Answer none to the installer's tracker question, or put TICKET_ID_REQUIRED=0 in ~/.himmel/himmel.conf; that file applies to every project on this machine.
  4. The install itself starts uncommitted. Main now refuses commits, so the installer offers to make the one allowed commit there (chore: add himmel), or prints the command that does. Until the install is committed, a new worktree has none of himmel's files, so Claude runs there without its hooks.

In the project folder

  • Three hook entries, a status line and HIMMEL_REPO in .claude/settings.json.
  • Three git hooks in .git/hooks. Existing ones are saved as <hook>.himmel-backup and still run after himmel's.
  • Claude Code plugins, recorded in .claude/settings.json; the preview names each one.

In your home folder

  • A himmelctl launcher in ~/.local/bin, a cache in ~/.claude/himmel.
  • A trust entry for the project in ~/.claude.json.

Only if bun is installed

  • The qmd search tool, about 2.1 GB of search models, and an index of your himmel clone.

Left alone

Your notes vault, scheduled jobs, the Telegram bridge and the second-model reviewers.

Every part the installer can add is one item of the install manifest, 48 items in all, 38 of them in the starter install, and himmelctl status checks each one. The full reference: Install on your project.

Undo

From the project you installed into, node ~/himmel/scripts/himmelctl/bin.js uninstall --yes removes what the install added and restores what it replaced. Add --dry-run first to see the list; anything it cannot undo by itself is listed under NEEDS YOU.

1Ship with guardrailsEdits and commits on your main branch, direct pushes to main and reads of secret files are refused. A guard against destructive shell commands is on by default.

Every change Claude makes lands on its own branch in its own worktree, and the moves that can hurt a project are refused before they run.

Turn it on

Included in the starter install, the destructive-command guard too.

What you get
  • Worktree isolation

    Claude may not edit files while your checkout is on main. The refusal names the command that cuts a worktree: bash scripts/worktree.sh feat/<scope>.

  • Secret-file protection

    Reads of .env files, keys and similar secret files are refused. To read one on purpose, start Claude Code with READ_SECRETS_OK=1 for that session.

  • Git gates: commit, message, push to main

    If your project has no .pre-commit-config.yaml, the install places himmel's own git hooks. They refuse a commit on main, a direct push to main, and a commit message without a conventional type and a ticket reference such as #1. No tracker? Put TICKET_ID_REQUIRED=0 in ~/.himmel/himmel.conf.

  • Destructive-command guard

    On by default. It refuses rm -rf, git reset --hard, git clean -f, force pushes and similar before the command runs. To run one on purpose, start Claude Code with DESTRUCTIVE_OK=1 for that session.

  • /pr-check review panel

    Reviews a branch before its pull request opens: Claude reads the diff (and a second model family too, once you add one at Level 4), you rule on each finding, and a round repeats until nothing blocking is left.

Try it

Three refusals you will meet

› Ask Claude to read .env

You see
⛔ block-read-secrets: refusing Read of secret file: ~/your-project/.env
Run
$ git push origin main
You see
ERROR: Direct push to 'main' is not allowed.
Open a PR from a worktree branch instead.

› Ask Claude to run rm -rf build

You see
block-destructive-commands: destructive command refused (recursive rm); bypass: DESTRUCTIVE_OK=1 in the launching shell (per run)

Each of Claude's refusals names a one-session bypass, which you set when you start Claude (for example READ_SECRETS_OK=1 claude), never per command. The push-to-main gate has no bypass: changes reach main through a pull request.

You need
  • Level 0.
  • A git repository with a main branch.
Setup time

Not measured yet.

What it costs
  • No model usage for the guards and gates.
  • /pr-check uses your Claude usage for each review round.
Turn it off

For one session: start Claude Code with EDIT_ON_MAIN_OK=1, READ_SECRETS_OK=1 or DESTRUCTIVE_OK=1. For good: node ~/himmel/scripts/himmelctl/bin.js uninstall --yes.

Who it is for

Anyone who installs himmel.

2Second brainYour notes vault fills and links itself on a schedule, and Claude's lessons land in it.

A link you drop into your vault at midnight is a connected, summarized note by morning, and search over it stays fresh.

Turn it on

Run the installer again and pick the luna profile; it scaffolds a vault (or uses yours) and offers the scheduled jobs below.

What you get
  • Your vault, from the template

    Start from the bundled templates/luna-second-brain/ or a vault already made from it. Any folder of notes is not enough.

  • Scheduled jobs

    Recurring jobs on your system's scheduler (cron). You see a row only when its condition holds, and anything you decline is recorded as declined.

    Scheduled jobs: pick from 6
    JobWhat it doesOffered when
    pipelineDaily: pulls in what you clipped and writes summaries into the vault. Uses your Claude usage.a vault exists
    qmdDaily: re-indexes the vault for search. No model usage.a vault exists
    graphmapHourly: refreshes the map of links between notes, no model usage; a weekly deeper pass uses Claude.a vault exists
    vault-stallEvery 15 minutes: notices when the vault stops saving itself to git, clears a few known harmless causes, and alerts you.a vault exists
    codex-sweepCleans up leftover processes from the OpenAI reviewer.you turned on the GPT reviewer (Level 4)
    doctorDaily health check of your install; reports, fixes nothing.always

    Not offered on the trail (4):

    • drift-fix: A maintainer job that bumps himmel's own pinned upstreams; the installer hides it on a starter install.
    • upstream-watch: A maintainer job that watches himmel's own upstream pull requests and issues; the installer hides it on a starter install.
    • repo-sync: Needs a platform himmel no longer supports; never offered on Linux or macOS.
    • pull-cadence: A personal health-data connector, offered only when its own token is set; not part of the trail.
  • Vault search (qmd)

    Local search over your vault. Re-indexing is its own job: arm only the pipeline and your search goes stale.

  • Clip triage (obsidian-triage)

    /triage-clips summarizes and tags Web Clipper output in Clippings/ and moves action items to today's daily note. /synthesize-clips finds patterns across clips.

  • Obsidian skills (claude-obsidian)

    Comes from upstream, pinned to a release tag; not a himmel fork.

  • Note graph (graphify)

    A map of how your notes link to each other, kept current by the graphmap job.

  • Memory compounding: /memory-compound

    Claude Code keeps a memory index for each project and loads it into every session, within a fixed budget. When the index nears that budget, run /memory-compound in a session of its own. It moves the lasting lessons into vault notes, checks that qmd search finds them, and only then trims the index. The vault notes land on a branch for you to review and merge. It runs when you ask; there is no schedule.

$ bash ~/himmel/scripts/luna/qmd-cadence.sh status

You see whether the job is armed, its schedule and its last run. arm refuses to arm it twice, and disarm removes exactly what arm added.

You need

  • A vault made from templates/luna-second-brain/.
  • bun, for qmd search (about 2.1 GB of models).
  • cron on Linux or macOS.

Not measured yet.

What it costs

  • Search re-indexing and the hourly graph refresh: no model usage.

Turn it on

  • Alerts

    Scheduled jobs and health checks send their alerts to the same chat.

4Review depthA second model family (OpenAI GPT, on your ChatGPT/Codex subscription) reviews every diff alongside Claude, and its track record tunes the review.1 preview1 planned

Every /pr-check round is read by two model families, and you can see which reviewer's findings hold up.

Turn it on

Answer codex to the installer's lanes question (after codex login), or run the install again with --with-codex.

What you get
  • OpenAI GPT critic, via hermes

    A critic is one reviewer model; hermes is the open-source agent runtime himmel uses to call it. With hermes installed and your ChatGPT/Codex login in place, /pr-check calls the GPT critic beside Claude.

  • /cr-scores critic scorecard

    Every /pr-check round records its findings and verdicts in a review ledger on your machine. /cr-scores shows, for each critic, how many of its findings held up and how often it was available, and says when a critic is worth dropping.

  • /cr-tune tuning proposals

    Drafts tuning proposals from the findings that were disproved, each citing its ledger rows, and never applies them itself.

  • /cr-learnings-refresh known findings

    Updates the list of known findings from the ledger, and from a CodeRabbit learnings export if you use CodeRabbit.

  • Free hermes criticspreview

    Critics on free model tiers, called the same way. Early: works, still changing.

  • Multi-model front endplanned

    One place to drive Claude and the other model families side by side. Not built yet.

5Spend & contextHeavy work checks your remaining usage first, and each session can read its own context fill.1 planned

You see how full each session's context is, and scheduled work waits instead of eating the usage you need for your own sessions.

Turn it on

The status line comes with the starter install; the usage check runs by itself before scheduled work.

What you get
  • claude-hud status line

    Shows the model, the context fill and your usage under every prompt. The install backs up your old statusLine and uninstall restores it.

  • Usage preflight

    One word before a heavy run: go, or wait and why. Scheduled runs check it before they start, because they spend the same usage as your own sessions.

  • Self-read context fill

7Command a fleetMany workers ship tickets in parallel under one chief, and you watch them live.2 preview2 planned

You hand the chief a list of tickets, and workers ship them in parallel, each through the same review and merge gate as your own changes.

Turn it on

/chief new starts a chief; himmelctl ui opens the fleet view.

What you get
  • Written briefs for each worker

    A worker is one Claude session that owns one ticket, one worktree and one pull request. The chief writes each worker a brief with its scope and the files it may touch.

  • Parallel workers, started in waves

    The chief is the session you talk to: it hands out the tickets, starts workers in parallel waves, and keeps them off each other's files.

  • Coordination in writing, not memory

    Every worker reports in its handover note and by message, so a chief that hands over its shift loses nothing.

  • Merge only on the chief's approval

    A worker merges only when CI is green at its exact commit, every review point is decided, and the chief has approved that commit.

  • Session run view

    himmelctl ui serves a local page on 127.0.0.1 behind a per-launch key. Its Fleet page lists every live Claude session; click one to follow it as it runs.

  • Fleet boardpreview

    With a chief running, the same page groups the workers under it and shows each one's stage and whether it waits on you. Works, still changing.

  • Release managerpreview

    A session that rules which tickets go into each version and reports the burn-down. Works, still changing.

  • Trends over days and weeksplanned

    Throughput and cost per merged change, over time, from real runs. Not built yet.

  • Installable chief moduleplanned

    The chief and its scripts as one installable part for your own project. Not built yet.
